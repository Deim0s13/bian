# BIAN alignment, terminology, and source policy

## Objective

The project will be BIAN-native while remaining an independent open-source
project. Every statement represented as BIAN must be attributable to an
authoritative BIAN source for a declared release. No project inference or
customer-specific concept may be presented as BIAN-defined.

This is the operational meaning of “100% aligned to BIAN”: **100% of content
attributed to BIAN is source-traceable and unaltered in meaning**. It is not a
claim that BIAN defines 100% of the product or that the project is endorsed by
BIAN.

## Why the distinction is essential

BIAN defines banking architecture concepts and publishes artefacts such as the
Service Landscape and Semantic APIs. The proposed product also needs concepts
that are outside BIAN's role, including:

- a fictional bank's applications, technologies, owners, and dependencies;
- mapping workflow, review status, inference confidence, and remediation;
- security profiles and platform enforcement details;
- jurisdiction-specific regulation and control evidence;
- vendor claims, product coverage, and commercial decisions;
- open-source project governance and software operations.

Calling these “BIAN” would itself be misalignment. They must connect to BIAN
without masquerading as BIAN content.

## Mandatory information classes

### Class A: Authoritative BIAN assertion

Imported from an allowlisted BIAN-controlled source. It must retain:

- BIAN release;
- official identifier where available;
- exact official name and definition;
- BIAN artefact type and lifecycle/registration state;
- source location and immutable digest or equivalent version evidence;
- source licence/rights classification;
- import time and importer version;
- any detected source ambiguity or inconsistency.

Only Class A may be described as “defined by BIAN.”

### Class B: Mechanically derived BIAN projection

Produced deterministically from Class A without adding business meaning, for
example a normalised representation or generated format. It must link to every
source assertion and disclose the derivation and tool version.

It may be described as “derived from BIAN [release],” not “defined by BIAN,”
unless the output itself is an unmodified BIAN artefact.

### Class C: Project extension

Defined by this open-source project, such as review state, confidence, evidence
status, workflow, security-profile application, or transformation planning.

It must use a project namespace and documentation. It may refer to Class A but
must not be stored or displayed as a BIAN artefact. Class C is project context,
not an analytical inference. A project-generated claim or recommendation is
Class E even when it uses a Class C method or workflow.

### Class D: Customer or fictional-bank assertion

Describes a bank's applications, APIs, data, owners, mappings, decisions, or
estate. For HSB it must be explicitly marked synthetic. For any future adopter,
it remains customer-owned information even when it uses BIAN terminology.

### Class E: Inference or recommendation

Generated by rules, analytics, or AI. It must disclose evidence, method/version,
confidence or uncertainty, and review status. It is never promoted to Class A.

### Class F: Third-party assertion

Includes vendor claims, regulatory interpretations, or external mappings. It
requires its own source, rights, scope, owner, and review state.

## Source allowlist and rights register

No BIAN source enters the product without a reviewed source-register entry:

| Field | Requirement |
|---|---|
| Source owner | BIAN e.V. or explicitly authorised publisher |
| Location | Stable official URL/repository/package location |
| Artefact scope | Exact files, endpoints, models, or documents covered |
| Release/version | Explicit and independently recorded |
| Integrity | Commit, digest, signature, or documented capture method |
| Licence/terms | Licence text and any access/use conditions |
| Allowed use | Import, modification, generation, distribution, hosted use |
| Attribution | Required notices and display obligations |
| Trademark | Permitted descriptive use and prohibited implications |
| Review | Reviewer, date, unresolved questions, and re-review trigger |

## Current preliminary source position

As of 17 August 2026:

- BIAN's official public GitHub repository describes itself as a repository of
  BIAN artefacts, currently Semantic APIs, and lists R14 OpenAPI and AsyncAPI
  variants: <https://github.com/bian-official/public>.
- That repository contains the Apache License 2.0:
  <https://github.com/bian-official/public/blob/main/LICENSE>.
- Apache 2.0 permits use and redistribution subject to its conditions, including
  retaining relevant notices and marking modified files. It explicitly does not
  grant permission to use the licensor's trade names, trademarks, service marks,
  or product names beyond customary source attribution.
- BIAN's Service Landscape page describes the landscape as the reference
  structure organising Service Domains and lists Release 14.0:
  <https://bian.org/deliverables/service-landscape/>.
- The broader BIAN website states that its content is copyrighted. Public access
  must therefore not be treated as a blanket open-source licence for portal,
  model, diagram, training, or documentation content.

This is a preliminary product-policy record, not legal advice. Before importing
or redistributing content, the project must review the exact source package and
terms and, where necessary, obtain written clarification from BIAN.

## Terminology rules

1. Use the exact official BIAN term and capitalisation for the selected release.
2. Store the source definition; do not replace it with a project paraphrase and
   call the paraphrase authoritative.
3. Do not infer an official hierarchy or relationship from naming similarity.
4. Do not invent Service Operations for a Service Domain that lacks them.
5. Do not call a customer application a Service Domain. Record that it implements,
   supports, consumes, or maps to a Service Domain using an explicitly defined
   project relationship.
6. Do not describe a mapping score as BIAN conformance unless BIAN publishes and
   authorises that exact conformance method.
7. Use release-qualified language whenever BIAN meaning or content may differ by
   release.
8. Keep original identifiers even if a display alias is required for usability.
9. Record official deprecation, rename, and registration status rather than
   silently replacing old terms.
10. Treat project module names beginning with “BIAN” as working names subject to
    trademark and affiliation review before public release.

## Conformance gates

A BIAN-attributed release or feature cannot ship unless:

- all BIAN assertions originate from allowlisted sources;
- source integrity and release are reproducible;
- terminology and relationships pass automated comparison with the source;
- transformations have full lineage and deterministic tests;
- unsupported artefacts and source gaps are reported, not filled by invention;
- project extensions are distinguishable in storage, APIs, UI, exports, and docs;
- required licences, notices, modifications, and attribution are present;
- no wording implies BIAN endorsement or certification without evidence;
- a designated BIAN-conformance maintainer approves the evidence record.

## Permitted claim pattern

Prefer narrow, reproducible language:

> This release imports the listed BIAN 14.0 Semantic API files from the official
> public repository at commit `<commit>`. Source digests and transformation
> lineage are included. Project extensions and HSB data are separately marked.

Avoid claims such as:

- “100% BIAN compliant”;
- “official BIAN platform”;
- “BIAN certified”;
- “all banking semantics are BIAN-defined”; or
- “BIAN-aligned” without release, scope, method, and evidence.

## Change management

Every new BIAN release, source, or terminology change requires:

1. source-rights and integrity review;
2. model-level comparison with the prior source;
3. terminology and relationship conformance tests;
4. impact analysis for project extensions and HSB scenarios;
5. updated attribution and notices;
6. review of public conformance wording;
7. a versioned conformance report.
